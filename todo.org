** DONE Can we speed up the Homebrew cask reinstall chain? This seems to be happening in serial currently
    Batched into a single `brew reinstall --cask a b c ...` call instead of
    looping one `brew` invocation per cask (brew.py:brew_upgrade_casks). Each
    separate invocation paid its own Ruby interpreter startup + dependency
    resolution cost; batching removes that per-cask overhead. The `r` and
    `gpg-suite*` post-install hooks now run once after the batch via
    membership checks instead of per-iteration. Not a full parallelization
    (Homebrew doesn't safely support concurrent installs), just removal of
    repeated per-invocation overhead.

** DONE Our Julia version checker is getting confused by LTS channel
    Root cause: julia had no _SPECIAL_CASES entry in version_check.py, so it
    fell back to GitHub's /releases/latest, which returns whatever was most
    recently published with no concept of version ordering -- an LTS patch
    (1.10.12) published after the true latest stable (1.12.7) shadowed it.
    Added _check_julia() (version_check.py), which reads the GitHub tags list
    and picks the highest vX.Y.Z by semver instead of by publish date.
    Verified live: now returns 1.12.7, matching the app.json pin.
** DONE Does it make more sense for the koopa builder machine to just bundle python from uv?
    Decision: keep building from source on the builder. Switching to uv's
    python-build-standalone prebuilt binaries would decouple Python from
    koopa's own openssl3/readline/sqlite/etc. builds and its dependency-rebuild
    tracking (dep_revisions/stale_revdeps) -- not worth losing that control.
    Every binary-enabled (non-builder) machine already skips the source build
    entirely: it just pulls the tarball the builder already built and pushed
    to S3 (_can_install_binary()/install_app_from_binary_package). The builder
    is the only machine paying the source-build time at all, once per version
    bump, and that one-time cost is an acceptable tradeoff to keep control.
