** DONE Hitting binary push issue for Python packages on builder machine with uv
    Root cause: 'push_app_build()' and 'push_missing_app_builds()' picked the
    version to push with 'sorted(os.listdir(app_dir))[-1]' — a string sort over
    sibling version directories under app/<name>/. app/python3.13/ holds
    3.13.13/3.13.14/3.13.15 today; a single-digit patch release (e.g. 3.13.9)
    sorts after 3.13.15 as a string, so the old logic would silently check S3
    for and push the wrong version. Both now read the version actually linked
    at opt/<name> (realpath + basename) via a new '_active_app_version()'
    helper in install.py, matching what the CLI handler
    '_handle_push_app_build()' already did correctly. 'push_app_build()' now
    raises explicitly when opt/<name> isn't linked instead of guessing.
    Also moved the auto-push call in 'install_app()' to after
    '.install/revision' and '.install/info.json' are written (previously
    before), so a pushed tarball carries build provenance instead of a bare
    prefix. Added unit tests covering the wrong-version-picked scenario for
    both functions and the not-linked error case.

    `bootstrap.sh` now reads `etc/koopa/vendor.json` directly (own JSON parse via
    whichever `python3` it finds, `sed` fallback if none exists) and routes every
    source download through it, honoring `vendor_first`/`vendor_only`. Fixed a
    live bug along the way: the koopa-mirror fallback URLs for openssl and python
    were 404ing (`src/openssl/`, `src/python/`) because they didn't match the
    app.json keys (`openssl3`, `python3.12`) that `koopa develop mirror-src`
    actually uploads under — `install_openssl`/`install_python` now derive the
    right name (python's tracks `.python-version` at runtime).

    Added a `http.remotes` map (host -> remote-proxy repo, exact then
    `.suffix` match) so a `vendor_only` network can resolve `github.com`,
    `koopa.acidgenomics.com`, etc. through a remote-proxy repository
    with zero pre-population — one entry proxying
    `koopa.acidgenomics.com` covers every source tarball koopa already
    mirrors there. `koopa.vendor.vendor_rewrite_url()` (Python) and
    `vendor_rewrite_url()` (the sh port in `bootstrap.sh`) implement this

** DONE I hit a weird edge case where Python reinstalled with `koopa update` after I just installed them with `koopa reinstall` first
    Root cause: python3.13/python3.14's app.json 'dependencies' is a dict keyed
    'default'/'firewall_linux'/'firewall_macos'. '_resolve_dep_dict()'
    dispatches on 'has_firewall() or can_build_binary()' — empty list in a
    plain shell, 11 C libraries under KOOPA_BUILDER=1 or behind a firewall.
    check.py's staleness check re-resolved this dict *now* and compared
    against the recorded '.install/info.json', defaulting any dep never
    recorded to revision 0 — so an app installed in one context (empty deps
    recorded) re-checked in another (11 deps re-resolved) saw a phantom
    'bzip2 revised: 0 -> 2' and got rebuilt from source, matching the reported
    7m05s/4m52s timings exactly.
    Fix: added 'recorded_app_deps()' in app.py, reading the dep list actually
    resolved at install time from '.install/info.json' (an authoritative empty
    list is distinguished from "nothing recorded"). check.py, 'stale_revdeps()',
    and '_apps_with_missing_runtime_deps()' now all prefer this recorded list
    over re-resolving app.json's dict, falling back to live re-resolution only
    for installs that predate this field. Also made 'update_stale_apps()' print
    per-app reasons unconditionally (previously gated behind --verbose), so a
    future rebuild explains itself instead of looking arbitrary. Added
    regression tests reproducing the exact phantom-dependency scenario in both
    check.py and app.py's stale_revdeps().
